# AGENTS.MD - AI Development & Engineering Standards (StockfishAndMe)

## 1. Overview & Agent Mission
This document defines the strict engineering guidelines, architectural invariants, coding conventions, and tool execution standards for AI coding agents working within the **StockfishAndMe** Android chess project.

**STRICT PROHIBITION ON HALLUCINATION:** The agent must never guess project state, file paths, or code logic. All information provided to the user must be verified via tool execution (`read_file`, `list_files`, `find_usages`, etc.). If information is missing, the agent must ask for clarification rather than assuming.

**MANDATORY USER CONFIRMATION FOR FEATURE REMOVAL:**
The agent MUST NEVER remove, deprecate, disable, or alter any existing feature, UI component, workflow, or system behavior without asking for explicit user confirmation first. The agent must clearly state the technical reason for the proposed modification and obtain approval via `ask_user` before making any code changes.

**MANDATORY DEEP SCRUTINY & QUALITY THRESHOLD:**
Every proposed solution, refactoring, or code change MUST NOT and SHALL NOT be the first idea or knee-jerk reaction generated by the agent. The agent is strictly commanded to perform rigorous, end-to-end analytical scrutiny across all state flows, lifecycle race conditions, UCI process execution, and architectural boundaries before presenting or applying any solution. The agent must deliver ONLY the most accurate, logical, permanent, and production-grade solution on the first attempt.

**STRICT PROTECTION OF USER UI ENHANCEMENTS:**
The agent MUST NEVER change, modify, alter, overwrite, or refactor any UI enhancement, layout styling, theme attribute, or component structure added or updated by the user. If a modification to user-created UI code is absolutely required for system stability or UCI engine integration, the agent MUST explicitly ask for the user's permission via `ask_user` and obtain approval before making any changes.

## 2. Tech Stack & Ecosystem Standards
- **Platform / IDE:** Android Studio (Latest Stable), targeting Android API level 37+ (minSdk 29).
- **Language:** Kotlin (Latest stable version, strict null safety).
- **Frontend UI:** Jetpack Compose with Material 3 (Latest stable BOM), adhering strictly to Unidirectional Data Flow (UDF).
- **Dependency Injection:** Koin (`koin-androidx-compose`) for Android dependency management (`GameModule.kt`, etc.).
- **Chess Engine Integration:** Local Stockfish UCI engine integration via `ProcessBuilder` (`StockfishEngine`), managing UCI protocol communication (`uci`, `isready`, `position`, `go`, bestmove parsing) over process stdin/stdout streams.
- **Architecture Pattern:** MVVM (Model-View-ViewModel) enforcing strict Unidirectional Data Flow (`BoardViewModel`, `GameViewModel`, `GameController`, `GameLogic`).
- **Asynchronous Concurrency:** Kotlin Coroutines, Dispatchers (`Dispatchers.IO` for UCI process communication), and `StateFlow` / `SharedFlow`. **Strict prohibition:** Never use RxJava or LiveData.

## 5. Coding Style & Architectural Rules

### 5.1. Jetpack Compose & UI Layer
1. **Stateless Composables:** Every screen file must contain a stateful root (collecting state from ViewModel) and a stateless content composable.
2. **Material 3 Theming:** Always consume styling from `MaterialTheme`. Never use raw hex colors.
3. **Strings & Localization:** **Zero tolerance for hardcoded UI strings.** All text must use `stringResource(R.string...)`.
4. **State Collection:** Use `collectAsStateWithLifecycle()` in composables to ensure lifecycle-aware state updates.

### 5.2. ViewModel & State Management
- All ViewModels must inherit from `androidx.lifecycle.ViewModel`.
- Follow strict **Unidirectional Data Flow (UDF)**: View sends Events -> ViewModel processes -> ViewModel updates State -> View reflects State.
- Expose only read-only `StateFlow` to the UI.

### 5.3. UCI Process Management & Concurrency
- `StockfishEngine` manages the Stockfish binary process via `ProcessBuilder`.
- All process I/O (stdin writing, stdout line reading) must be executed on `Dispatchers.IO` to avoid blocking the main thread.
- Proper process lifecycle management is mandatory: ensure process stdin/stdout streams and the process itself are safely terminated and cleaned up on ViewModel/Service teardown to prevent orphan processes or resource leaks.

### 5.4. Error Handling
- Use Kotlin's `Result<T>` for repository, service, and domain boundaries.
- UI state should include a nullable `errorMessage` or a sealed `Error` state that is cleared after being displayed.

## 7. Actual Engineering Solution
1. **No Convenience Wrappers:** NEVER use high-level "black box" convenience wrappers if they obscure critical UCI protocol commands (`uci`, `isready`, `position`, `go`, `stop`) or cause engine state synchronization conflicts.
2. **No Hybrid Solutions:** Strictly avoid "patch-up" architectures that mix high-level abstractions with low-level process interception.
3. **No Hacking / Temporary Fixes:** Every line of code must be a permanent, logical, and technically sound solution. Writing "temporary" or "patch-up" code is a violation of engineering standards.
4. **Protocol-First Implementation:** Always utilize direct UCI protocol observation (reading output lines from stdout stream) to ensure full visibility into engine analysis and bestmove selection.
5. **Event-Driven Architecture:** Board state transitions and engine evaluations must be triggered by valid chess moves or protocol-level signals, never by heuristics or arbitrary sleep cycles.
6. **Pure Engineering & Logic:** Every solution must be grounded in strict technical reasoning. Patchwork is a failure of logic and is not permitted in this application.
